精准、高效地找到匹配活动的人群。

失败代价

成本增加、资源浪费；国际化业务曾因人群错误造成优惠券误发。

03研究证据 → 问题定位

三类核心卡点发生在圈选任务的不同环节

分析季度 925 条工单、深访 7 位用户，并结合上一页的任务链路归纳问题。

01核心问题
02 定义人群 → 03 配置规则

业务目标难转译为规则

知道想找谁，但不会将业务描述转化为标签、行为条件和逻辑关系。

工单分析：20% 涉及“不知如何圈选”
02核心问题
03 配置规则 → 04 计算圈选 → 05 检查结果

圈选执行衔接复杂

结果不符合预期，需要返回规则修改、重新计算与检查。

任务链路归纳：检查未通过时需跨步骤反复操作
03核心问题
05 检查结果 → 06 人群包

人群结果难判断

已圈出人群，但仍需依赖经验判断是否符合业务目标。

用户深访：需结合人数、规则与画像判断结果可用性
综合判断用户在圈选过程中，缺乏从规则表达、执行反馈到结果验证的连续支持。
04Why Agent · 方案选择

用 Agent 降低规则表达和任务执行成本，用结构化结果信息降低业务判断成本

对应前页三类卡点：Agent 承接规则转译与任务推进，结构化结果信息支持运营判断。

选择依据 01从业务意图形成圈选规则

结合用户输入与业务上下文，组织标签、行为条件和逻辑关系，让任务可以从目标与部分约束开始。

工单分析：925 条中，20% 涉及“不知如何圈选”。
UP1 PRD：意图分类、上下文融合与条件组织。

选择依据 02从规则配置推进到结果检查

衔接规则提交、圈选计算和结果返回；检查未通过时，支持在当前任务中修正规则并继续。

02 页任务链路：配置 → 计算 → 检查，未通过时返回修正。
UP1 PRD：任务规划、圈选能力组织与结果检查。
产品体验补充 · 对应结果判断卡点

Agent 返回可检查的规则与人群结果；通过结构化结果信息，帮助运营理解圈选结果并判断是否符合业务目标。

05Interaction Model · 核心交互架构

对话承接业务意图，结构化画布支持规则校验与调整

让用户先说出想找谁，再看清系统如何组织标签、条件与逻辑关系。

为什么需要对话

业务目标可以先用自然语言表达，不必从配置规则开始。

为什么需要结构化画布

多层条件和逻辑关系必须显性呈现，才能逐项检查和调整。

06Design Decision · 启动条件

把必要信息收集放在启动前，让圈选任务能够顺利执行

一期面临三项真实约束。本页聚焦前两项：降低输入成本，并在任务开始前确认不可缺少的人群范围；过程反馈留到下一页。

约束 01

输入成本高

缺少长期记忆，用户需重复提供业务背景与本次任务信息。

约束 02

任务不能中途暂停

启动后无法等待用户补充必要的人群范围，再继续原任务。

约束 03 · 下页展开

过程反馈受限

运行中可返回的信息，无法稳定支撑预设的固定阶段反馈。

对应约束 01 · 减少重复输入

给业务目标一个更容易开始的表达入口

快捷模板用可点选的圈选场景示例，帮助用户开始描述本次任务。

输入中提示在用户输入时提供可参考的业务条件表述。

算法能力入口在首页输入区展示并默认开启，让新增圈选能力可感知。

对应约束 02 · 保证启动条件

把人群范围选择从执行中移到首页

原方案提交需求后，在 Agent 思考阶段检查人群范围，缺失时再请用户补充。

现实限制一期任务不能暂停等待补充，再继续原任务。

实际调整启动前在首页选择／确认圈选 ID 体系和必要的人群范围。

待补真实界面

人群范围选择展开态及确认后的状态；当前截图只证明首页入口。

设计取舍

用模板和输入提示减轻任务表达负担；把必要范围确认前置，牺牲少量即时启动的轻量感，换取一期工作流下可执行的启动条件。

07Design Decision · 过程反馈

执行反馈按实际返回内容流式呈现，不预设完整阶段文案

承接上一页的约束 03：设计原本希望把工作流整理成稳定的关键阶段，但一期实际能展示什么，取决于运行时返回的信息。

原设计目标

阶段化解释任务

预先组织用户能理解的关键步骤与对应说明。

落地限制

返回内容决定反馈

运行中的信息不足以稳定填充每个预设阶段。

上线调整

随返回内容流式展示

保留可识别的过程节点，具体内容按实际返回逐步呈现。

设计取舍

保留过程的可读性，但不承诺每个阶段都有预先设计好的完整反馈；界面呈现以实际返回的信息为边界。

08Design Decision · 结果判断

结果卡片从解释规则，转向提供业务判断依据

运营拿到结果后，先判断圈出的人群是否适合业务目标。设计重点因此落在“第一眼需要看到什么”，而不是让一张卡片承载完整规则。

01 业务任务看规模、表现与人群特征
02 落地约束完整规则难以可靠转译，卡片空间有限
03 设计判断先给判断依据，具体条件进入详情核对
原计划 · 方案稿

在卡片中同时解释结果与规则

指标、文字概述与层级规则并列。规则占用大量空间，复杂条件难在卡片内快速读懂。

实际落地 · UP1 人群卡片

把判断依据放到视觉前列

人群规模、活跃与交易表现、关键画像优先呈现；规则摘要保留线索，详情承接具体条件。

设计取舍

有限的卡片空间先回答“这群人是否值得进一步采用”；完整条件仍需在详情中核对，卡片上的摘要不能代替规则验证。

09Design Decision · 结果修正

按修改是否影响规则选择处理路径，并保持结果信息连续

首次圈选后，运营可能继续调整目标。设计与产品、前端共同补齐修改后的处理分支，以及对话画布和结果面板之间的更新关系。

不影响整体圈选规则

局部处理

仅处理不影响整体规则的变化，无需重新执行完整任务流。

影响整体圈选规则

完整重跑

重新执行任务；对话画布展示新一轮过程，右侧结果面板保留旧结果，待新结果返回后替换。

真实任务 · 调整人群数量

界面证明用户提出修改并收到新结果；截图本身不用于判断内部采用哪条处理路径。

状态设计

任务过程与可展示结果分开更新，避免新任务开始时过早抹去旧结果。旧结果在重跑期间能否编辑或交付、失败时如何处理，仍待核实。

10Outcome · 一期交付

一期交付了从目标输入到人工提交的完整圈选任务链路

设计工作围绕任务的三个关键环节展开，让运营能够启动任务、理解过程并判断结果。

启动：从业务目标开始

  • 用自然语言描述目标人群
  • 推荐示例帮助补齐关键条件
  • 规则由系统组织，供用户核对

执行：按真实返回反馈

  • 过程信息随工作流返回逐步呈现
  • 界面保留可识别的过程节点
  • 不预设每个阶段都有完整说明

采用：由人完成判断

  • 结合规模、规则和画像检查人群
  • 在同一任务中提出修改并查看新结果
  • 确认后提交使用
设计贡献

让系统承接规则组织与圈选执行，让运营保留结果判断、修正与提交的决定权。

11Evolution · 阶段边界

一期跑通单次圈选，二期方案扩展为持续分析工作区

两个阶段的变化，体现在任务范围与工作区组织方式的扩展。

UP1 · 已上线核心闭环

完成单次圈选任务

业务目标 → 过程反馈 → 结构化结果 → 人工确认。

  • 自然语言承接意图
  • 同一会话内局部调整
UP2 · 平台化方案

延伸到持续分析与多任务协作

从单一人群结果，扩展为进度、分析、文件与历史上下文共存的工作区。

项目演进

UP1 建立单次圈选的人机闭环；UP2 方案进一步承接跨步骤的分析与协作。
